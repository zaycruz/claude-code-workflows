### artifact-review-loop

When a document, plan, or spec must be reviewed, revised, and re-verified in one run. Args: {artifact (text, required), focus?, maxRounds?=3 (1-5), jev?, risky?}. The parent adopts or discards the returned artifact. Ported from Pi jev.artifact-review-loop.

1. **Review round** — Fresh parallel lenses + fresh arbiter (Claude) judge the current text
2. **Rewrite round** — Clanker (no Edit/Write tools) returns the full revised artifact; Claude Sonnet rewrites if the clanker fails or the input is risky (risky text skips the clanker)
3. **Settle** — approved | max-rounds | stagnated | blocked-needs-decision | rewrite-failed | review-failed

### clanker-loop

Default way to get execution work done cheaply with review. Args: {tasks: [{id, prompt, risky?, checks?: [cmd]}] | string, checks?: [cmd], setup?: [cmd], checksTimeout?: seconds, maxRounds?=3 (1-5), model?=the installed executor (sonnet by default), explainer?=false}. A plain string is one task. explainer: before the clanker edits a module it has not read in this task, it writes a 10 to 20 line explainer (what it does, callers, invariants) and ends its report with them, so the reviewer and the coordinator get the context; off until its token cost is measured on the reviewer eval set, and each result then carries explainerCost. checks default to what the repo declares (package.json scripts, Cargo, go, pytest, make test). risky = production, CI gates, auth, secrets, schemas or migrations (Opus reviews). risky is also derived from the diff: a change under .github/, scripts/ci/, migrations, auth, RLS policies, billing or secrets paths makes the task risky from that round on (Opus reviews, the result says ownerApproval); the risky the caller passes can only add to that, never remove it. Run from inside the git repo the tasks change; each task returns its worktree for the coordinator to merge, plus preExisting findings (reported, never blocking), closed findings and suppressed re-reports.

1. **Execute** — a worker (the executor model, or the fallback) does the task in its worktree
2. **Checks** — the checks step (clanker-checks on Haiku, or checks-runner with no model) runs the tests and linters and writes a report
3. **Review** — Sonnet (Opus for risky, by the caller or by the paths the diff touches) reviews the diff with the checks report: pass, pass_with_nits or block; from round 2 it verifies open findings by id and reviews only what changed
4. **Probes** — the checks step runs the reviewer's edge-case probes: a failing probe is a blocker and re-runs every later round
5. **Escalate** — After maxRounds blocked rounds, the fallback model is asked to rethink the approach once and is reviewed again

### council

A material decision with real tradeoffs. Args: {question (required), scope?, nonGoals?, advisors?: string[] (stance descriptions, 2-4), maxPasses?: 2|3, risky?: boolean (supervisor on Opus), advisorModels?: string[] (model names; default rotates the executor and fallback models by advisor index)}. Ported from Pi /council.

1. **Pass 1** — Independent advisor reports
2. **Claim matrix** — Supervisor: agreements, disputes, missing proof, relay packets
3. **Cross-exam** — Advisors answer curated challenge packets (pass 2, optional pass 3)
4. **Memo** — Supervisor writes the decision memo

### engineering-review-loop

Opt-in deep audit only: a risky merge (production, CI gates, auth, secrets, schemas, migrations, money) or an explicit request for a deep review. Not the default and not chained after clanker-loop: clanker-loop (one reviewer plus deterministic probes) builds and reviews everyday work, and on the loop-bench it shipped clean code for about a sixth of this loop's Claude cost. Args: {repo?, baseRef?="main", maxRounds?=3 (1-8), task?, focus?, strict?=false, risky?=false (Opus reviews; production, CI, auth, secrets, schemas, migrations), checks?: [one-line cmd] (checks runner commands; list the lint, format, typecheck and build commands the repo defines, default = what the repo declares), setup?: [one-line cmd], checksTimeout?=seconds, maxEngineers?=3 (1-4), tracker?="auto"|"beads"|"github"|"none", jev?}. Reviews the checked-out branch plus uncommitted changes against baseRef. A plain string is a focus; "implement: ..." implements first. Verdict: green | green-untested | max-rounds | stagnated | blocked-needs-decision | fix-failed | no-root | review-failed | review-inconclusive | implement-failed | implement-noop.

1. **Implement** — Optional: one clanker implements args.task in the working tree
2. **Checks** — checks-runner runs builds, tests and linters with no model (its report is the only test evidence); before Implement it runs once with no project commands just to report the repository root
3. **Review** — Per dimension: Claude peer and adversary review independently with the checks report
4. **Cross-exam** — Per dimension: each reviewer confirms, disputes, or refines the other one's findings
5. **Consolidate** — One consolidator merges all dimensions, settles disputes from source, verifies prior blockers
6. **Engineer** — Clanker engineers fix the consolidated findings, one per disjoint file group
7. **Log** — A clanker files every improvement the loop did not apply in the tracker (beads by default; GitHub only when asked)

### feature-pipeline

After a human confirms a feature request at intake (Slack thread, ticket), run from the feature branch the change belongs on. Args: {brief (required; the confirmed request verbatim), baseRef? (accepted, unused: the build worktree starts from HEAD), checks?: [one-line cmd], setup?: [one-line cmd], maxRounds?=3 (1-5), risky?=false}. Returns the final spec, the assumptions decided for the reviewer, and the build result with its worktree dir. The coordinator merges the worktree and owns the branch, the commit, and any push. For a deep multi-reviewer audit of a risky merge, run engineering-review-loop on the merged branch as a separate step.

1. **Context** — research, clarify mode: scout + researcher + synthesis (its questions get answered as assumptions)
2. **Spec** — clanker writes title, spec, assumptions, acceptance as JSON
3. **Spec review** — artifact-review-loop over the spec (2 rounds)
4. **Build** — clanker-loop implements the spec in a worktree: checks, one reviewer, probes

### gather-context

Alias of research mode clarify. At the start of a fuzzy task, to ground it and surface the questions to ask the user (the parent asks the returned questions with AskUserQuestion). Args: {intent (required), skipExternal?: bool}; checked here (unknown keys are rejected), then passed to research, which does all the work. Ported from Pi /gather-context-and-clarify.

1. **Gather** — Scout (local) and researcher (external) in parallel
2. **Synthesize** — Known facts and open clarification questions

### parallel-research

Alias of research mode answer. Grounding an answer or decision in sources and the local codebase. Args: {question (required), angles?: string[]}; checked here (unknown keys are rejected), then passed to research, which does all the work. Ported from Pi /parallel-research.

1. **Research** — One agent per angle, in parallel
2. **Synthesize** — What we know, local implications, tradeoffs, gaps, next move

### red-blue-loop

Standing bug hunt on a repo, by hand or on a schedule (tools/red-blue-run.sh). Run from inside a checkout of the target repo at base. Args: {base (required, e.g. "origin/staging"), repo?: absolute checkout root (checked), targets?: [path | "PR #n"], seeds?: [suspicion text], known?: [titles already reported], lenses?: [drift|fakes|errors|concurrency|limits|pii-sends | custom text], maxFindings?=6 (1-20 per round), maxRounds?=2 (1-5), redCmd?="npx vitest run {files}", checks?: [cmd] (the fix must also pass these), setup?: [cmd], checksTimeout?: seconds, fix?=true, model?=the installed executor (sonnet by default)}.

1. **Preflight** — checks runner: the checkout HEAD is base
2. **Find** — one read-only clanker per lens lists suspicions
3. **Prove** — per suspicion, a clanker in its own worktree writes only a failing test
4. **Check** — checks runner (no model) runs the red command twice; both runs must fail
5. **Verify** — 3 Claude skeptics try to refute each proven finding; 2 must fail to
6. **Fix** — clanker-loop per confirmed finding: restore the red test, smallest fix, red command + checks

### research

Ground a fuzzy task or an answer/decision in sources and the local codebase. Args: {question (required; intent is an alias of it), mode?: answer | clarify (default answer), angles?: string[] (max 5; answer mode - custom angles run on clankers, which use curl for web access), skipExternal?: bool (clarify mode - drop the web researcher)}. mode clarify = the old gather-context: at the start of a fuzzy task, to surface the questions the parent should ask the user (AskUserQuestion). mode answer = the old parallel-research: what we know, local implications, tradeoffs, gaps, next move. Read-only. Ported from Pi /gather-context-and-clarify and /parallel-research.

1. **Gather** — clarify mode: scout (local) and researcher (external) in parallel
2. **Research** — answer mode: one agent per angle, in parallel
3. **Synthesize** — known facts and open clarification questions (clarify); what we know, local implications, tradeoffs, gaps, next move (answer)
